# Parking Lot

本文档记录当前先不做的事项。进入实现前，需要重新评估优先级、依赖条件和对现有工作流的影响。

## Memory V2

```text
事项：
实现用户画像、长期对话摘要、业务产物向量记忆和按任务类型注入。

为什么暂时不做：
当前主干流程、G1/G2/G3 边界和统一调度方式尚未冻结。过早接入长期记忆会放大 Agent 边界不清、记忆注入位置不清和用户隔离风险。

未来可能在哪个阶段做：
Stage 4 之后，或原 Phase H。

依赖条件：
稳定的 workflow_type、Agent 边界、Run/Step 状态、用户隔离策略和记忆关闭策略。
```

## RAG reranker

```text
事项：
为 RAG 检索结果增加二次排序或 reranker，提高 chunk 相关性。

为什么暂时不做：
当前任务是冻结主干流程，不处理检索质量专项。过早引入 reranker 会改变 G1/G2/G3 的输出基线，不利于后续比较。

未来可能在哪个阶段做：
Stage 4 之后，或作为 Phase E 质量评估后的 RAG 专项。

依赖条件：
稳定的评测集、当前 RAG baseline、召回和引用准确率指标。
```

## PDF OCR

```text
事项：
增加 PDF OCR，处理扫描件或图片型文档。

为什么暂时不做：
当前知识入库和文档解析不是主干流程的阻塞点。OCR 会引入新的依赖、耗时、错误来源和文档质量评估问题。

未来可能在哪个阶段做：
Stage 5 之后，或文档解析专项。

依赖条件：
明确的扫描件需求、OCR 引擎选择、版面还原策略、质量评估样本和人工复核流程。
```

## 多模态文档解析

```text
事项：
解析图片、图纸、截图、表格图片等多模态材料。

为什么暂时不做：
当前主干仍以文本、结构化输入和已有业务产物为主。多模态解析会扩大输入范围，容易影响 Router、Graph 和 Tool 边界。

未来可能在哪个阶段做：
Stage 5 之后，或独立多模态资料处理阶段。

依赖条件：
明确的文档类型、文件上传契约、解析结果 Schema、引用定位方式和人工校验机制。
```

## Graph 并行化

```text
事项：
将可并行的 Graph 节点改为 fan-out/fan-in，例如 Sales Collaboration 中 R&D 和 Quality 并行。

为什么暂时不做：
当前阶段只写主干文档。并行化会增加状态合并、失败恢复、超时、重试和幂等复杂度。

未来可能在哪个阶段做：
Stage 4 之后，或原 Phase G。

依赖条件：
稳定的串行结果 baseline、结构化交接协议、Run/Step 状态模型、超时和部分失败策略。
```

## FMEA -> Audit -> Report 自动串联

```text
事项：
用户生成 FMEA 后，系统自动接 Audit，再自动生成 Report。

为什么暂时不做：
当前 FMEA、Audit、Report 都是独立工作流。自动串联会模糊用户意图、增加错误传播风险，并要求统一产物适配层和人工确认节点。

未来可能在哪个阶段做：
Stage 5 之后，或原 Phase F/I 之后。

依赖条件：
Workflow Registry、统一 Run/Step、明确的产物适配层、人工确认机制和错误回滚策略。
```

## 复杂任务取消 / 恢复

```text
事项：
支持长任务取消、暂停、恢复、重试单步和断点续跑。

为什么暂时不做：
当前 Run/Step 还未全系统统一。先做复杂恢复会绑定到某个局部实现，后续容易返工。

未来可能在哪个阶段做：
Stage 4 之后，或原 Phase G/J。

依赖条件：
统一 run_id、步骤状态、幂等键、节点输入输出快照、失败分类和重试策略。
```

## 前端统一任务中心

```text
事项：
在前端提供统一任务中心，展示 QA、PFMEA、Audit、Report、Proposal 的任务状态和历史结果。

为什么暂时不做：
当前后端还没有统一 Workflow Registry 和统一 Run/Step。前端先统一会缺少稳定事实来源。

未来可能在哪个阶段做：
Stage 5 之后，或原 Phase D 的后续扩展。

依赖条件：
统一任务查询 API、workflow_type、状态枚举、权限隔离和历史结果摘要格式。
```

## 长期案例系统

```text
事项：
建立质量案例或项目案例实体，将 FMEA、Audit、Report、Proposal 等业务产物关联到同一案例。

为什么暂时不做：
当前不应使用 session_id 冒充业务案例 ID。案例边界、自动匹配规则和人工确认流程还未定义。

未来可能在哪个阶段做：
Stage 5 之后，或原 Phase I。

依赖条件：
明确的 case_id / quality_case_id、业务产物关联模型、候选匹配算法、人工确认入口和错误关联回滚机制。
```

## 生产级 tracing / token / cost 监控

```text
事项：
记录节点级 tracing、token、模型调用次数、延迟、错误率和成本。

为什么暂时不做：
当前阶段只冻结主干流程。生产级观测需要稳定节点命名、Run/Step 模型和模型调用封装，否则指标口径会反复变化。

未来可能在哪个阶段做：
Stage 4 之后，或原 Phase J。

依赖条件：
稳定 Graph 节点、统一 Run/Step、模型调用包装层、日志脱敏策略和成本口径。
```
